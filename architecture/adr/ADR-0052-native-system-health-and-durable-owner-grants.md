## One coordinated Internal Native3 contract

Native3 uses version/profile3,22 startup sources,720 startup bytes,912 manifest
bytes and a2560-byte catalogue in the existing readonly catalogue page. The extra
source is an actual separately built faulty Shell image, with its own descriptor,
roles and hash. Complete A/B packages, ordinary child budgets, Root32KiB stack,
W^X, guards, retained hardware ownership and source/image checks remain mandatory.
Old Desktop wire encodings and behavior stay distinct. Native3 Root's exact
ProcessIdentity38 cap0 call uses the four-output ABI and returns the actual
capture tick in R10, matching the independent NativeSelfIdentity receipt. All
SourceRoot self-query callers use call4; child ProcessCONTROL queries and old
Desktop/provider preserve legacy R10. This delivered-IRQ clock value is timing
metadata, never authority or a System-health verdict. Any required increase to
Native Root's private image admission must be justified by the new actual ELF,
remain inside its existing512-frame quota and preserve all other actor bounds.

RootSystem adds only GrantPolicy wire48..61 -> physical96..109. Existing System
16..29, AppRegistry64..77, AppData80..93 and File Notes32..45/Private48..61 physical
regions remain disjoint. Apps never receive this window or generic sector rights.
A single Root backend serializes reborrowed Store devices; there is no second
Rust owner of a shared window and no formatting after ordinary open errors.

## Real System selection and recovery

The bounded Good/Bad cohorts may share the same actual protected Root and common
Block/Display/File/Input images while selecting different measured Shell images.
Their distinct generation/cohort identities bind the exact whole recipe. This
is a real System implementation difference, not a fake fault marker or a promise
of arbitrary Root/driver upgrades. Root and the common backend prefix are verified
and booted before durable System selection; that existing Root is then bound by
actual self identity to BeginBoot/Admission. No new Root Start is invented at
BeginBoot and pre-selection execution is not mislabeled System health.

A versioned Native health contract names the selected critical Shell/graph and
fresh Root liveness. One anchored probation interval cannot be reset by foreign,
late or duplicate readiness, delayed report framing, or repeated observations.
Native3 Root self-identity mechanism38 with cap0 returns the actual capture tick
in its fourth output R10. Native3 callers use the explicit four-output wrapper;
child CONTROL queries and prior profiles retain their existing register contract.
Independent bounded Kernel receipts bind the actual Root identity, epoch,
incarnation, startup-manifest digest and capture tick. They certify that query,
not a Store decision. The first fresh query after durable Admission anchors the
one deadline; a later query independently witnesses liveness at promotion or
expiry. Framing and UART delays cannot move that anchor.

The current64-tick contract is preserved unless actual measurement justifies an
explicit separately versioned budget. Timely critical readiness, a real durable
System storage probe and fresh liveness are required before Known Good promotion.

During Managed probation, Root continues receiving actual readiness/events and
running health checks while deferring ordinary owner, App-transition and UART
work. Both direct App-mutation commands and queued transitions use the same
available-normal-graph predicate: SystemManaged requires current Healthy;
Standalone retains its existing operation; Recovery cannot launch normal Apps.
This prevents early activation from bypassing the ordinary launch health gate
or inserting unrelated Store work into the anchored critical interval.

A faulty Shell produces its actual crash capsule. Since the admitted Root remains
live, expiry without required critical progress is **MissingProgress**, not a
fabricated Root ProcessFault. The real deadline must elapse with fresh Root-live
observations; a short outer experiment bound cannot substitute for that event.
Store may select protected Good for the next boot after failure, while the current
admitted generation remains failed Bad until a genuine cold Good admission/health.
Staging Bad while Good runs similarly changes next selection, not current execution.

A protected recovery mode must offer a real owner path independent of the failed
normal Shell/graph. Its minimal path needs the trusted Root/Block backend and must
not require the failed normal generation to become healthy. Recovery selection,
cold return, actual GUI/App use and preserved data are executed on one continuing
owned disk. Current admission, selected next boot and Known Good are separate
inspector fields. Earlier M3 custody/recovery guarantees remain regression gates.

## Stable application data and content references

The existing complete-source build ID unnecessarily changes Native package IDs
after unrelated OS/document changes. Package build identity will instead bind
actual App ELF plus canonical App-specific metadata/resources. The outer build
manifest/catalogue retains complete source/Kernel build provenance. No publisher
or namespace authority follows from either digest. AppId, owner/schema identity,
full immutable package IDs and actual code admission remain separately checked.

Store format manifests are original creation provenance. Current compatible Root
admission is not permission to overwrite that history, reset app data or drop
referenced packages. Observers must validate original creation context separately
from current selection. The bounded demonstration retains exactly the needed A/B
containers through its Good/Bad/recovery modes; unavailable content fails closed.

## Durable explicit owner policy, fresh live authority

The existing grant-policy library owns one explicit latest owner/App READ policy,
revision/digest/operation CAS, tombstone and move-only uncertain intent. A missing
policy is accepted as absent only after the whole region is verified blank. Only
an explicit owner action may allocate/remember; ordinary cold open never formats.

A real owner prompt binds actual current App/package/incarnation, stable File
object/revision/permission and READ/UntilRevoked. Old input is drained, the actual
prompt completes, and only a fresh complete exact confirmation is accepted. This
uses its actual owner-UART provenance and never fabricates GUI Present/Input or
sets picker-ready/submitted flags. Existing fresh GUI selected READ remains intact.
Inside the validated handoff, durable policy publication/readback precedes actual
capability enqueue; metadata or a saved session/handle is never live authority.

Native3 adds mechanism44 to enqueue a fresh managed READ using actual current App
ProcessCONTROL, actual readonly File source, exact managed GrantInbox and a fresh
nonce bound to an authenticated pending App Open. That may be the newly awaiting
Open or the exact same current unselected Open whose picker was already shown.
An actually submitted selection, completed request or reused nonce is refused.
Acceptance atomically consumes that Open and invalidates its old picker route;
Busy/refusal before acceptance preserves ownership. Kernel parses no durable
permission record and chooses no user policy. Old41 still requires genuine GUI
selection. SourceRoot/Shell distinguish interactive picker and remembered-policy
completion; cold remint must not masquerade as another picker approval.

Owner revocation first fences remints and App-data admission. A proposed Native3
mechanism45 uses the uniquely retained loaded owner to inhibit actual App dispatch
without revoking grants or recycling buffers. It may allow a pending outbound READ
to finish/wake, while preventing new App calls; an App which is an accepted RPC
callee must be refused before mutation so accepted work cannot be deadlocked.
Ordinary stop/revoke/reap occurs only after quiescence. Old37's Busy behavior stays
mutation-free. Held-target remint is refused by actual scheduler state as well as
SourceRoot policy. This closes the continuous-call starvation path without
pretending an accepted shared-buffer operation has already stopped.

The durable tombstone is acknowledged only after the required live authority is
retired and the exact Store publication/readback succeeds. Uncertainty retains
the actual operation/backend, fences further grants and never blindly retries an
accepted mutation. Cold/relaunch checks must not restore revoked/stale policy.

## Acceptance

Require actual explicit consent, durable remember, cold fresh remint, selected-only
read/denied mutation, real revocation and post-reboot refusal. Include malformed,
wrong subject/package/object/revision/nonce/source/inbox and pending-work cases.
Execute the combined graphical crash/restart -> Bad health failure -> cold Good
return plus independent basic recovery on preserved usable data. All actual linked
stacks, frame quotas, source/image bindings and final resource/authority retirement
must pass. Model/component results alone accept neither these mechanisms nor0.1.
