# ADR-0126 — Protected local development Install and Run

Date: 2026-11-16

Status: Implemented component; native installation qualification pending

## Context

ADR-0125 carries an independent complete `.zion` in measured Candidate-bank tail
space. That record creates no startup role, running instance, publisher trust,
storage allocation or installation permission. The existing dynamic image path
and ND private-data owner need an actual Root consumer with distinct protected
installation and execution decisions.

## Decision

Native Root offers separate **Install** and **Run** actions only when the actual
catalogue contains that ingress. Both protected dialogs display the full AppId,
package digest, executable digest, build identity and captured old Editor2
instance. A protected effect binds those facts, actual Root requester, a fresh
nonce and one original finite transfer cut. Ordinary app events and public or
private semantic requests cannot confirm either action. The fresh physical
gesture follows an actual accepted Root frame and Input barrier. Cancellation
before confirmation has no image or storage effects.

Install copies the exact measured source through the existing bounded dynamic
image owner, seals, verifies and registers it. ND compatibility is contextual:
actual Root handler/sole SystemIo readiness and authenticated loaded service
support must satisfy requirements. The historical registration context continues
to refuse unloaded ND requirements. Registration alone proves no execution.

The same native storage core used by tests then reads every sector in both fixed
external Registry and private-data regions before its first allocation write.
Any nonzero sector refuses. Only this explicit protected blank allocation formats
the fixed independently supplied descriptors. It creates schema1 private data
owned by the exact AppId and durably installs the exact package reference.
Failed, unformatted or foreign opens never trigger formatting. The one supported
pair does not imply a general allocator, update policy or multi-app installation.

Run first uses checked Registry open under the original descriptor and exact
immutable package resolver. Committed and pending payloads must validate before
recovery publication. A cold valid pending lifecycle can recover only that same
package. Foreign, corrupt, missing or incompatible package state refuses without
storage mutation. Durable Activate means selected software; it supplies no health
or successful-process claim.

Before reusing Editor2, Root seals ND admission under that same cut, requests a
clean Close, retires exact File authority through actual61 and service
reconciliation, performs actual STOP, drains RootEvents to actual empty, and
requires ND reply/storage debt quiescence. Only then may actual REAP scrub the old
surface and full inherited File window, close the old control and reuse the slot.
The new process comes from the exact registered capability, receives the existing
six-role FileApp grants, and remains Held through actual identity checks and
checked private-data enrollment. START follows enrollment and exact activation.
Completion additionally waits for authenticated Ready and settled app state.
The granted surface/present and focused-input roles also require explicit package
requests. Actual live control identity and the final accepted Root frame must
still validate before the original cut; later scheduler Yield is independent.

The running slot retains its full independent software identity and actual
captured process control. Requested selected-file rights are checked from that
software before any File grant. AppPrivateData never implies selected-file
access, and a package without A1 cannot acquire an A1 route through its slot.

## Failure and evidence boundaries

One original absolute cut governs accepted image, storage and lifecycle work;
child calls only clamp it. Unknown replies retain original operation, proposal,
transfer, held handles and exclusive storage/window owner. No automatic retry,
fallback package, cleanup publication, deadline renewal or drop-to-success exists.
Documented preaccept Busy/Full results may wait under the unchanged cut. A failed
installation can leave an explicitly incomplete allocation requiring separate
recovery work; this component provides no automatic repair or formatting path.

Host backend tests cover full-region blank preflight, exact cold activation,
foreign committed/pending refusal before writes, valid same-package pending
replay, unloaded ND refusal, original-cut uncertainty retention, protected full
identity binding and selected-file separation. These tests and native compilation
do not establish actual installation, startup, persistence across a real cold
boot, human approval, release signing, broad isolation or M8 acceptance. Native
VM evidence must retain the exact source, package, owner, device and observation
cohort before any such narrower runtime claim.
