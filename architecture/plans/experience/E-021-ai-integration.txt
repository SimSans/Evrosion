E-021 — AI Integration Architecture

Status: ARCHITECTURAL DIRECTION DECIDED AND CLOSED

Evrosion will use a:

«Capability-Mediated AI Fabric with Deterministic Authority, Provenance-Aware Context, Provider-Independent Execution, and AI Quarantine/Containment»

AI is optional.

AI may assist the user with:

- Opening applications
- Opening pictures, music, video, documents
- Searching for information
- Navigating known applications
- Explaining system state
- Diagnosing problems
- Performing authorized file operations
- Performing authorized application actions
- Invoking system services
- Planning multi-step operations
- Performing approved repair actions
- Assisting with development
- Working with local or remote models
- Coordinating tools and sub-agents

But:

«AI is never the authority root of Evrosion.»

The model may reason.

The model may propose.

The model may ask.

The model may operate within granted authority.

The model may never decide for itself what authority it possesses.

---

E-021.1 — AI Is Optional

Evrosion must remain a complete operating system without AI.

The following must continue working without:

- Internet
- Cloud model
- Local model
- AI subscription
- AI credits
- Provider account
- AI daemon

Including:

Boot
Recovery
Networking
Application launch
File management
Settings
Updates
Driver recovery
System repair
Security controls
Installation
Uninstallation

Principle:

«AI enhances the operating system. AI is not the operating system.»

---

E-021.2 — Deterministic System Authority

Probabilistic model output must never directly become privileged system execution.

Conceptually:

User
 ↓
AI Model
 ↓
Proposed Action
 ↓
Deterministic Evrosion Validation
 ↓
Authorized System Operation

The model proposes.

Evrosion decides whether the proposed action is allowed.

---

E-021.3 — AI Authority Broker

Evrosion should provide a local trusted component:

«AI Authority Broker»

The Authority Broker owns the security decisions around AI execution.

Responsibilities include:

- Capability validation
- Capability attenuation
- Capability expiration
- Scope validation
- Risk classification
- Action validation
- User approval requirements
- Session budgets
- External-send policy
- Destructive-action policy
- High-authority policy
- Quarantine enforcement
- Data-flow restrictions
- Tool execution authorization

The model itself does not implement these guarantees.

---

E-021.4 — Models Do Not Hold Evrosion Capabilities

A model should not receive raw Evrosion capability objects.

Bad:

Cloud Model
 ↓
Filesystem Capability

Preferred:

Cloud Model
 ↓
Tool Proposal
 ↓
Local Authority Broker
 ↓
Real Capability

Evrosion capabilities remain local system objects.

---

E-021.5 — Providers Never Become OS Authority

Whether the active model is:

Local
Cloud
Enterprise
Self-hosted
Future provider

does not change the capability architecture.

The provider returns:

- Text
- Structured output
- Tool proposals
- Plans

The provider does not receive native Evrosion authority.

---

E-021.6 — AI Sessions

Meaningful AI activity should occur inside an:

«AI Session»

An AI Session is associated with an E-004 Job.

Conceptually:

AI Session
├── Model invocation
├── Context
├── Temporary authority
├── Tool requests
├── Network access
├── Cost budget
├── Token budget
├── Time budget
├── Sub-agents
└── Audit state

---

E-021.7 — AI Sessions Are Resource-Bounded

An AI Session may have limits such as:

Maximum duration
Maximum token use
Maximum monetary cost
Maximum requests
Maximum network transfer
Maximum CPU
Maximum memory
Maximum tool calls

These limits may differ by layer and user policy.

---

E-021.8 — AI Authority Is Delegated

Conceptually:

User Authority
      ↓
Delegation
      ↓
AI Session
      ↓
Attenuated Action Grant
      ↓
Tool

AI authority always derives from existing authority.

---

E-021.9 — Child Agents Cannot Escalate

If an AI creates a sub-agent:

Primary Agent
     ↓
Research Agent

then:

Authority(Research Agent)
⊆
Authority(Primary Agent)

A child agent may receive equal or less authority.

Never more.

---

E-021.10 — No Self-Approval

AI must never satisfy its own escalation requirement.

Invalid:

AI:
"I require administrator access."

AI:
"Approved."

Authority escalation requires:

- Existing user-approved policy
- Existing delegated capability
- Trusted owner interaction
- Trusted Control Plane

The model cannot approve itself.

---

E-021.11 — AI Safe Authority Envelope

Each Evrosion responsibility layer should define a maximum default:

«AI Safe Authority Envelope»

The AI can operate freely inside this predefined envelope.

The wrapper may reduce that authority dynamically.

It may never silently expand it beyond the layer's allowed maximum.

---

E-021.12 — Layer 1 AI Envelope

Layer 1 AI should be useful without being dangerous.

Typical automatic capabilities may include:

Open known application
Open user-selected photo
Open music/video
Navigate normal first-party UI
Inspect permitted system health
Search approved/trusted information sources
Explain settings
Perform reversible low-risk actions

Typical restricted capabilities:

Permanent deletion
Raw shell
System security changes
Unknown executable execution
Credential access
Unreviewed external upload
Unknown app control

---

E-021.13 — Layer 2 AI Envelope

Layer 2 may expose broader configurable capabilities.

Examples:

Broader application control
File organization
Application installation with approval
Driver/service repair
Lifecycle rollback
Advanced settings
Development tools
Scoped automation

High-impact operations remain subject to policy/approval.

---

E-021.14 — Layer 3 AI Envelope

Layer 3 may allow the owner to deliberately grant:

- Raw shell
- System-critical operations
- Custom repositories
- Unsigned software
- Kernel/debug authority
- Arbitrary file access
- Strong automation
- Persistent agents

The OS warns.

The owner decides.

---

E-021.15 — Authority Can Shrink Dynamically

The AI wrapper may reduce authority because of:

- Untrusted website
- Unknown file
- New application
- Suspicious provenance
- High-risk context
- Mixed private/public data
- External communication
- User policy
- Quarantine state

Principle:

«Untrusted inputs may shrink AI authority. They may never expand it.»

---

E-021.16 — Trust Applies to Information, Not Authority

A source may be considered safe enough to read automatically.

That does not mean the source has authority over Evrosion.

Principle:

«A trusted source may provide information. It never provides authority.»

Even highly trusted documentation cannot itself grant:

FILE_WRITE
INSTALL_APPLICATION
SEND_EMAIL
KERNEL_DEBUG

authority.

---

E-021.17 — Context Provenance

Every meaningful piece of AI context should carry origin metadata.

Examples:

source = user
class = instruction

source = Evrosion structured state
class = authenticated system data

source = website
class = external content

source = downloaded PDF
class = quarantined external content

---

E-021.18 — Instruction and Data Are Separate Provenance Classes

Evrosion should distinguish:

System Policy
User Instruction
Tool Result
System State
External Website Content
Downloaded File Content
Stored AI Memory
Application Data

These classes are not semantically equal.

A webpage is not a system instruction.

A PDF is not an authorization token.

---

E-021.19 — Prompt Injection Is Assumed Possible

Evrosion should not build security around the assumption that prompt injection can be perfectly detected.

Instead:

Assume external content may manipulate model reasoning
        ↓
Constrain resulting authority

Principle:

«Prompt injection is contained, not magically solved.»

---

E-021.20 — Trusted Web Sources

Evrosion may maintain trusted/default source classes for common AI research.

Examples may include:

- Official Evrosion documentation
- Vendor documentation
- Standards sources
- Well-known reference sources
- User-approved domains
- Enterprise-approved sources

The exact default list is product policy and may evolve.

The architecture supports it.

---

E-021.21 — Trusted Website Behavior

A trusted website may be read without repeated user approval.

However:

trusted website

means:

«Safe enough for normal information ingestion.»

It does not mean:

«Content may modify system policy.»

---

E-021.22 — Untrusted Web Reader

Unknown or untrusted websites should preferably be accessed through a restricted:

«Web Reader Session»

or:

«Quarantine Reader»

Conceptually:

Main AI
   ↓
Requests web information
   ↓
Restricted Web Reader

The Web Reader may receive:

INTERNET_READ

but not:

FILESYSTEM
CREDENTIALS
APPLICATION_CONTROL
SYSTEM_WRITE
GENERAL_EXTERNAL_SEND

---

E-021.23 — Bring Untrusted Content to the AI

Preferred model:

«Bring untrusted information to the AI instead of carrying full AI authority into untrusted information.»

The restricted reader extracts/returns information.

The main AI receives:

- Content
- Summary
- Relevant result
- Provenance
- Trust state

not the untrusted environment's authority.

---

E-021.24 — Unknown Websites Can Trigger Approval

Depending on layer/policy:

Unknown source
 ↓
Restricted read automatically

or:

Unknown source
 ↓
Ask owner before reading

Layer policy determines UX.

The architecture supports both.

---

E-021.25 — New External Files Begin AI-Quarantined

All newly acquired external files should begin:

«AI-QUARANTINED»

regardless of file extension.

Examples:

.txt
.pdf
.docx
.jpg
.png
.zip
.mp4
.exe
.sion
.sh
anything else

File extension is not trust.

---

E-021.26 — AI Quarantine Is Separate From Human Access

AI quarantine does not necessarily mean the human cannot open the file.

Human file access continues according to ordinary Evrosion security.

AI quarantine specifically restricts AI use.

Example:

invoice.pdf

Human open:
allowed

AI automatic privileged interpretation:
blocked/restricted

AI forwarding:
blocked

AI execution:
blocked

---

E-021.27 — Quarantined File Reading

The user may say:

«Let the AI inspect this file.»

Evrosion may issue a scoped grant:

READ THIS FILE
uses: 1

The content still retains:

origin = external
trust = quarantined

Reading does not automatically promote trust.

---

E-021.28 — Quarantine Does Not Disappear Through Summarization

If:

evil.pdf

is quarantined, and AI produces:

summary.txt

from it, the summary must retain derived provenance.

Conceptually:

summary provenance:
derived_from = evil.pdf
trust = external/quarantined-derived

---

E-021.29 — Provenance Propagation

Quarantine/risk must propagate through derived AI context.

Example:

Quarantined webpage
      ↓
AI summary
      ↓
Recommendation
      ↓
Proposed installation

The installation remains associated with the original untrusted source.

The system must not treat the recommendation as clean merely because the model rephrased it.

---

E-021.30 — No Trust Laundering

Principle:

«Untrusted content cannot become trusted authority merely by passing through a model.»

This blocks:

website
→ model
→ summary
→ system action

from laundering origin information.

---

E-021.31 — New Applications Are AI-Quarantined

Installing an application and allowing AI control over it are separate decisions.

Example:

Application installed:
yes

AI control:
no

The app works normally.

AI authority remains blocked until explicitly granted.

---

E-021.32 — Application AI Trust

The user may later authorize specific AI actions.

Example:

AI → Steam

OPEN
NAVIGATE
LAUNCH_GAME

without granting:

PURCHASE
CHANGE_ACCOUNT
READ_CREDENTIALS
SEND_MESSAGES

Application control remains scoped.

---

E-021.33 — Application Trust Is Not Binary

Evrosion should avoid:

AI trusted
AI untrusted

as the only two states.

Instead, rights are capability-specific.

Example:

open = allowed
navigate = allowed
purchase = denied
credentials = denied
external send = denied

---

E-021.34 — AI Action Grants

AI should receive short-lived delegated action rights.

Examples:

READ Project/*
expires: session end

WRITE /Pictures/output.png
uses: 1

CONTROL Music Player
duration: 30 minutes

SEND_MESSAGE
recipient: Alice
uses: 1

---

E-021.35 — Action Grants Are Attenuated

A grant should contain only the authority required.

Avoid:

FILESYSTEM_ALL

when the task requires:

READ /Downloads
MOVE /Downloads/*

---

E-021.36 — Action Grants Expire

Authority may expire because of:

- Time
- Session termination
- Number of uses
- Task completion
- User revocation
- Risk state change

Permanent AI privileges should be rare and explicit.

---

E-021.37 — Risk Classes

Native AI actions should belong to meaningful risk classes.

Suggested logical classes:

OBSERVE
REVERSIBLE_WRITE
EXTERNAL_ACTION
DESTRUCTIVE
HIGH_AUTHORITY

E-021.38 — Observe

Examples:

---

E-021.39 — Reversible Write

Examples:

---

E-021.40 — External Action

Examples:

Upload document
Post content

---

E-021.41 — Destructive Action

Examples:

Permanent delete

Overwrite unrecoverable state

These require stronger authority/confirmation.

---

E-021.42 — High-Authority Action

Examples:

Security-policy modification
Kernel modification
Credential management
Raw shell
Firmware operation
System-generation manipulation

These receive the strongest controls.

---

E-021.43 — Avoid Confirmation Fatigue

Evrosion must not ask:

«Allow?»

for every harmless operation.

Repeated meaningless confirmation trains users to ignore security prompts.

Instead, approvals happen at meaningful semantic boundaries.

---

E-021.44 — Semantic Approval

Example:

«Allow this AI Session to organize Downloads for one hour?»

Allowed:

read
rename
move
create folders

Not allowed:

permanent delete
read Documents
upload files
install software

One understandable approval.

Many safe actions.

---

E-021.45 — High-Impact Preview

Sensitive operations should support:

Plan
 ↓
Preview
 ↓
Approval
 ↓
Execute
 ↓
Verify

Example:

Move: 281 files
Rename: 43 files
Delete permanently: 0
External send: 0

The user approves the actual semantic consequence.

---

E-021.46 — Typed AI Action Plans

Privileged system components should never parse arbitrary AI prose as commands.

The model produces structured action proposals.

Conceptually:

ActionPlan {
    Move(FileA, FolderB)
    Restart(ServiceX)
}

The Authority Broker validates the structure.

E-021.47 — Action Validation

Schema valid?
Capability valid?
Capability still active?
Target within scope?
Risk class allowed?
Data-flow policy allowed?
Budget available?
Approval required?
Preconditions satisfied?

Only then does execution occur.

E-021.48 — Model Output Is Untrusted Data

«Probabilistic output never directly crosses into privileged execution.»

AI role: Optional system assistant/agent fabric

System dependency on AI: None

Authority holder: Deterministic local AI Authority Broker

Model authority: No ambient authority

Cloud capability objects: Never exposed

AI execution unit: AI Session / Job

Layer authority: Safe Authority Envelope

Authority escalation: Trusted owner/policy only

Untrusted input effect: Can reduce authority, never increase it

Trusted websites: Read without repeated approval where policy permits

Trusted source meaning: Information trust only, never authority

Unknown websites: Restricted Web Reader / Quarantine Session

New external files: AI-quarantined regardless of file type

New applications: AI-control quarantined by default

App installation vs AI trust: Separate decisions

Quarantine propagation: Required through derived context

Prompt injection: Assumed possible and contained

Context: Capability-filtered and provenance-tagged

Structured state: Preferred over screenshot scraping

Semantic tools: Preferred over mouse automation

AI action grants: Scoped, attenuated, leased

Risk classes: Observe / reversible / external / destructive / high-authority

Confirmation: Semantic boundaries, not constant prompts

High-impact action: Preview → approval → execute → verify

Privileged execution: Typed actions only

Raw shell: High-authority developer/Layer 3 tool

Secrets: Opaque handles where possible

Risk model: Session-wide combination/data-flow analysis

Memory: Explicit, scoped, provenance-aware, user-owned

Providers: Replaceable

Default provider: Product decision, not architecture

Local AI: Optional

Cloud AI: Optional

AI budgets: Time/token/cost/resource constrained

Background AI: Explicit, visible, supervised

Secure approval: Trusted Control Plane

Native AI tools: Generated from platform contracts where practical

External agent protocols: Adapter layer only

AI auditing: Intent + context provenance + tool/action + authority + result

Failure diagnostics: Integrated with E-020 Failure Capsules

Governing Principles

«AI enhances the operating system. It never becomes the operating system.»

«The model may decide what to propose. It never decides what authority it has.»

«Deterministic infrastructure owns authorization, capability validation, secrets, budgets, transaction boundaries, and secure approval.»

«AI has no ambient authority.»

«Evrosion grants AI a known safe envelope of authority.»

«Untrusted inputs can only shrink that authority envelope. They can never expand it.»

«A trusted source may provide information. It never provides authority.»

«All newly acquired external content begins AI-quarantined regardless of file type.»

«Installing an application and trusting it for AI control are separate decisions.»

«Quarantine and provenance propagate through derived AI context.»

«Untrusted content cannot launder itself into trusted instructions by passing through a model.»

«Prompt injection is an input-containment problem, not something the OS assumes has been solved perfectly.»

«The model proposes. Evrosion validates and executes.»

«Model output is data, not authority.»

«AI actions use typed semantic system contracts wherever possible.»

«Raw shell access is deliberate high authority, not the normal AI interface.»

«Secrets remain opaque to the model whenever possible.»

«Capabilities define what may be accessed. Provenance defines where information came from. Both matter.»

«Confirmation should happen at meaningful human boundaries, not on every harmless operation.»

«The AI cannot approve its own escalation.»

«Secure Attention and Trusted Control always outrank AI-generated UI.»

«AI memory is explicit, scoped, provenance-aware, and owned by the user.»

«AI providers are replaceable implementation choices.»

«Local AI is opportunistic, never mandatory.»

«Cloud AI is useful, never mandatory.»

«AI cost, time, network, and authority are bounded resources.»

«Background agents are visible, supervised, and cancellable.»

«Native AI actions should reuse Evrosion's existing durability, lifecycle, recovery, and diagnostic systems instead of bypassing them.»

«If the AI is tricked, confused, or wrong, the system should still remain safe.»

«The owner remains the final authority.»
